# KOYO Studio 用户功能可用开发计划

日期：2026-10-03（Asia/Taipei）

## 1. 目标与来源

目标：让用户能够注册登录、购买套餐或积分、使用各工作台完成真实任务、保存和下载作品，并在失败时得到正确的费用处理。

后端模型来源按用户要求收敛为两类：

1. RunningHub 聚合 API。用户已说明 runninghub.ai 账户完成充值，优先核验并接通这条渠道。
2. 各模型厂商官方 API。按已配置凭证、可用额度、模型能力、成本和稳定性接入。

RunningHub 作为首批联调优先渠道；正式路由按每个模型的能力、成功率和已核实成本配置。终端用户使用 KOYO 账户和积分，供应商凭证由服务端保管。

## 3. RunningHub 接入前要核对的内容

官方文档区分 Model、LLM、AI App、Workflow 四类 API。Model API 与 LLM API 要求 Enterprise-Shared API Key；AI App 和 Workflow 可用的 Key 类型更广。需要确认充值与 Key 属于同一账户主体，并核实目标 API 可消费的余额、并发额度和计费单位。[RunningHub 官方接入说明](https://www.runninghub.cn/runninghub-api-doc-en/)

媒体任务通常提交后取得 taskId，再查询结果。LLM 使用普通或流式响应，全球站公布的兼容入口为 `https://llm.runninghub.ai/v1`；要分别核实协议、模型能力与费用。[RunningHub LLM 入口](https://www.runninghub.ai/call-api/llm/models)

开发交付物：每个目标模型都有明确的内部 ID、实际供应商模型/端点、版本、能力、输入参数、价格来源、计费单位、额度与验收记录。未知费用不能当作零成本；人民币、美元和 RH 币按实际账单单位处理。

## 4. 分阶段执行

阶段描述的是交付顺序；全功能目标包含以下全部阶段。某项功能暂时隐藏或标记未开放只用于控制发布范围，不计为完成。

### P0-1：建立生产基线并定位供应商故障

- 重新核对线上工作目录、服务、构建、数据库迁移和工作树差异，制作并验证备份及恢复路径。
- 查明 providers degraded 对应的供应商和错误：认证、余额、端点、权限、限流或探针实现；依据证据修复。
- 核对 3 条公开目录记录为何不具备自动路由资格，检查前端展示与服务端下单使用同一可用性判定。
- 梳理用户可达 API 的真实上游；将正式可用渠道限定为 RunningHub 和已配置的官方渠道。历史任务保留原供应商关联，以便查询和对账。

通过条件：有可恢复的生产基线；目标供应商的认证、权限、余额与端点状态明确；普通用户只能下单到满足条件的渠道。供应商故障的根因不能用移除探针或伪造健康状态掩盖。

### P0-2：补齐统一生成、计费和结果处理

- 复用现有报价、GenerationJob、Worker、路由、存储和积分账本，打通 RunningHub 与官方适配器。
- 针对每个端点定义参数契约：提示词、参考图片/视频/音频、首尾帧、尺寸、时长、数量等；必填项和不支持的参数在提交前明确处理。
- 任务持久化保存供应商 taskId；刷新页面和 Worker 重启后继续查询。排队、运行、失败、成功和状态未知要可区分。
- 上游已接单或提交结果不明时先查询原任务，避免重试或切换渠道造成重复生成、重复成本。
- 备用渠道只用于同模型、同版本和兼容能力；不满足条件时向用户明确说明并重新报价。
- 报价显示与最终扣费使用可追溯的价格版本；成功结算一次，失败释放或退回一次。重复回调、重复点击和任务重试保持幂等。
- 平台用户积分与供应商费用分别记账；上游未退费也不能阻止应退给用户的积分，平台承担的成本要可核查。
- 将所有输出文件落到平台存储，保存完整结果列表、所属用户和历史关联；存储失败不能显示交付成功。

通过条件：真实图片任务和真实视频任务分别完成「报价 → 提交 → 供应商终态 → 存储 → 积分结算 → 历史 → 下载」，同时完成失败费用处理和重复提交验证。

### P0-3：打通账户与付费

- 注册、登录、验证邮件、找回密码、退出和重新登录可用。
- 订阅和积分包：下单、支付、回调验签、订单状态、权益、积分入账、账单查询一致；重复通知不重复发积分。
- 明确订阅到期、取消、退款和积分有效期规则，并落实到界面和后台。
- 用户只能访问自己的任务、作品、订单和工作区；管理员操作有权限和审计记录。

通过条件：受控测试账户完成实际流程；真实支付在指定账户及金额边界内执行，保存支付、订单和账本对应证据。

### P1-1：覆盖全部媒体工作台

每项先验收默认能力，再逐个加入已实测模型和参数组合。上架模型必须有成功记录；同一模型的文生图、图生图等模式分别验收。

| 功能入口 | 要完成的用户操作 | 验收结果 |
| --- | --- | --- |
| Image | 文生图、参考图编辑、尺寸/数量选择 | 上传成功、输出完整、作品可保存下载，费用一致 |
| Headshot | 上传人像、选择已支持风格并生成 | 输出关联输入任务，重新登录后可见 |
| Layers | 局部编辑、蒙版及实际提供的图层工具 | 坐标与尺寸正确，编辑结果能保存和导出 |
| AI Influencer | 创建角色并持续生成角色内容 | 角色资料持久化，参考素材实际传递 |
| Video | 文生视频、图生视频及已支持的首尾帧/参考视频模式 | 长任务能恢复，成品可播放和下载 |
| Motion Control | 人物图与动作视频驱动 | 文件及参数正确到达所选模型，结果可播放 |
| Lip Sync | 人像或视频配合音频生成口型 | 输入校验、音画同步、结果和计费可核查 |

| Audio | 语音合成、音乐及实际提供的音频处理 | 播放下载正常，按字符/时长/次等实际单位计费 |
| Clipping | 素材导入、片段处理、字幕和剪辑导出 | 有真实媒体处理和可播放的导出文件 |

媒体编辑、剪辑、合成和导出还需要平台自身的处理逻辑；每个功能要明确哪些步骤由 API 完成，哪些由平台完成。

### P1-2：迁移智能体、工作流、设计助手与应用

- **Agents：** 实现平台自己的智能体配置、会话、消息和附件保存；用 RunningHub LLM 或官方 LLM 执行推理，补齐流式输出、使用量计费、工具调用与权限。
- **Workflows：** 保存平台工作流定义；将 RunningHub 工作流 ID、输入节点、上传、执行、查询和结果映射到平台任务。既有流程按格式转换或重新绑定，不能直接假定两家工作流协议兼容。多步骤任务逐步记录成本和失败状态。
- **Design Agent：** 会话、画布、素材和工具执行归属平台账户；模型工具调用复用统一生成服务，保存项目并支持重新打开、继续编辑和导出。
- **Apps：** 将实际承诺给用户的应用绑定可执行模型、AI App 或工作流，具备输入表单、报价、运行、历史和结果。申请访问或静态卡片不计作功能完成。

通过条件：上述四类分别完成创建/打开、提交、真实执行、持久化、继续使用、费用核对和权限隔离；正式可用流程不依赖未纳入范围的第三方聚合服务。

### P1-3：完善共用页面与运营

- 素材库、生成历史、收藏、删除和下载：资源归属正确，刷新及重新登录后保持一致。
- 社区与分享：发布、查看、取消发布及实际开放的互动动作可用；私有作品不会自动公开。
- 账户、套餐、积分、订单、退款说明、帮助和政策入口：内容与后台规则一致。
- 管理后台：供应商凭证、额度、模型状态、价格、失败任务、订单、积分和用户权限可操作且有审计。
- 开放 API / MCP / CLI 入口如仍向用户展示，需要提供 KOYO 自有鉴权、限流、计费和可执行文档，并复用相同后端。
- 支持语言、移动端和键盘操作逐入口验证。涉及 UI 改动先读项目两个现行 UI 规范文件。

### P2：逐批开放并持续运营

- 每项功能按 Unknown → Testing → Active 管理；Testing 仅供受控测试，Deprecated 保留历史并禁止新建任务。
- 建立供应商余额、错误率、任务积压、超时、存储失败和费用异常告警；无可用渠道时在扣费前明确提示。
- 每批发布只包含验收通过的功能，保留功能开关和回滚版本；上线后复核相同用户路径。
- 每种对外开放能力至少有一个已验收的默认模型；扩展模型数量时复用同一验收表。

## 5. 统一验收记录

每条记录至少包含：日期、环境/构建、功能入口、测试用户、内部模型 ID、供应商/端点、参数、报价、平台任务 ID、供应商任务 ID、终态、全部存储资源、历史关联、实际积分变动、供应商费用或待对账状态、失败原因。

统一覆盖成功、输入错误、余额不足、供应商失败、查询超时、存储失败、重复点击/回调、页面刷新、Worker 重启和跨用户访问。超时但供应商终态未知时继续追踪，避免重复下单和重复结算。

验收状态只使用：未检查、待修复、待配置、待真实验收、已通过。功能覆盖率以实际通过的用户流程计算；页面数量、适配器数量和目录模型数量不计作完成率。

## 6. 下一批具体工作

1. 固定生产基线并确认 providers degraded 的具体原因。
2. 核对 RunningHub 账户主体、Enterprise-Shared Key、对应余额和目标端点。
3. 建立首批图片与视频的精确映射及价格，完成一张图和一段视频的完整交付与失败费用处理。
4. 完成账户、支付和积分闭环，形成首批用户可用版本。
5. 按媒体工作台 → Agents/Workflows/Design Agent/Apps → 共用页面及运营的顺序逐功能扩展。

真实付费验收前需要确定受控测试账户、可用官方供应商清单、总测试预算和单任务上限。优先检查服务器已有配置；凭证通过安全配置渠道维护，不写入计划或聊天记录。RunningHub 已充值记为用户提供的事实，充值金额、API 权限和可消费余额本次尚未查询。

本轮交付为开发计划及只读现状核查；没有修改业务代码、部署、重启服务、支付或提交付费生成任务。
